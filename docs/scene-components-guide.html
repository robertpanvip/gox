Gox scene 后端 · 复合组件使用指南

编译期 opcode + 常驻场景树 + 细粒度更新。组件只执行一次，靠 getter 保鲜、递归驱动。

gox build -jsx=scene runtime/scene Owner / Cleanup 条件分支 + Keyed For Go 1.27 泛型方法 示例已实测 go run ✓
核心一句：组件是一种「不透明的子树插槽」。骨架在编译期固定，组件的形状在运行时嫁接进来； 更新靠 getter 保鲜 + 递归透传，而不是重建整树或做 Diff。

一、工作原理（三段流程）

① 编译期

JSX 源码
<div>
  <Card title={t}/>
</div>
↓
opcode 模板（静态骨架）
OpElem   "div"
OpComp   "Card"  Slot:0
OpClose
N:1
getter（动态 part）
func() any {
  return Card(gxscene.Props{
    "title": func() any{ return t },
  })
}
组件调用只生成一次

② 首次 Render

gxscene.Render(tpl, getters...)
↓
骨架缓存
opcode 结构作 key：命中直接 clone；静态结构全仓库只解析一次。
↓
遇到 OpComp 槽位
调用 getter 一次 → 得到子组件 *Instance；组件函数之后不再执行。
↓
mountComp 嫁接
子实例的子节点挂到 <Card> 占位节点下；#frag 透明摊平，无多余标签层。

③ 每次 Update

t = "Gox" → view.Update()
↓
遍历所有 slot
文本/属性 getter() → 比较 → 变了才写
组件 child.Update() // 透传，不写
↓
递归进 Card
title getter 读到新值 → 只回写 <h1> 的文本节点。
Writes +1 · 零 Diff · 零重建
为什么组件要当「不透明插槽」：scene 的前提是「静态结构编译期确定、只解析一次」， 但组件形状是运行时才由函数决定的。把组件做成 OpComp 插槽——骨架里只固定「这里有个组件」， 真实子树首次渲染时嫁接进来——两边优势都保住：骨架完全静态可缓存，组件内部是独立常驻树。

二、完整例子（约束写在注释里）

可直接对照 examples/jsxscene.gx。每行关键点用 【约束 N】 标注。

// 构建：gox build demo.gx -jsx=scene
package main

import (
    gxscene "github.com/robertpanvip/gox/runtime/scene"
    "fmt"
)

// 【约束 1】复合组件签名必须是 func(gxscene.Props) *gxscene.Instance
// 【约束 2】组件只执行一次——函数体是「建树」而非「每次渲染」，
//           别在这里放依赖刷新的副作用
pub func Card(props gxscene.Props) *gxscene.Instance {
    // 【约束 3】动态属性用 Get[T]()() 读：先取 getter，再在 JSX 里 title()
    //   title 是 func() string 而非 string——写成 string 就成了不会更新的快照
    title := gxscene.Get[string](props, "title")
    n     := gxscene.Get[int](props, "n")
    return <div class="card"><h1>{title()}</h1><span>{n()}</span></div>
}

func main() {
    title := "GX"
    count := 1

    // 【约束 4】大写/带点标签 = 复合组件；其余 = 原生标签
    // title={title} 编成 getter（捕获变量本身），不是把 "GX" 拷贝进去
    view := <div id="app"><Card title={title} n={count}/></div>

    fmt.Println(view)   // 首次渲染：挂载常驻场景树

    // ——— 数据更新 ———
    title = "Gox"      // 改外部变量
    count = 2
    n := view.Update()   // 递归进 Card，只写变化的节点（此处 2 个）
    fmt.Println(view)
}

三、数据怎么更新

scene 后端没有 Diff、没有重建。更新 = 重新求值 getter + 只把变化的插槽写回节点。三种途径：

方式用法适用
闭包 getter title={title} 编成 func() any{return title}；改变量后调 view.Update() 外部普通变量；手动驱动
signal 自动接线
推荐		 view.BindReactive(signal.Effect) 一行接线；之后 count(5) 写 signal 即自动精确更新，无需 Update() 响应式 UI；signal 沿 Props 传到叶子，叶子在插槽里读
命令式
SetPart		 view.SetPart(slot, value) 按插槽下标直接写，绕过 getter 事件回调里精确改一个值；需知道 slot 下标，较少用 
view := gxscene.Render(tpl, getters...) // *Instance，常驻场景树
fmt.Println(view)                       // Instance.String() 用 TextBackend 绘制
n := view.Update()                      // 更新，返回写入节点数
// 只需渲染一次、不更新时：gxscene.RenderText(tpl, getters...) 直接返回 string

Update() 返回本次实际写入的节点数，值没变则写 0（equalValue 按类型严格比较）。 观测指标：Instance.Writes（累计写入，各 Instance 独立、不跨子树累加）、Instance.Updates（Update 调用次数）。

三·补充、signal 自动接线（一行搞定响应式）

scene 核心不依赖任何响应式库：BindReactive(effect) 接受一个形如 signal.Effect 的 effect 原语注入。它为每个插槽建一个 effect——普通插槽读 getter 后直接 SetPart（signal 变化只精确命中依赖它的插槽，不遍历全树）；复合组件插槽则递归进子组件接线（组件不重建）。signal 从根经 Props getter 一路传到叶子、在叶子的动态插槽里读取，写入即自动刷新。

// 完整可运行示例：examples/jsxscene-signal.gx
import (
    gxscene "github.com/robertpanvip/gox/runtime/scene"
    "github.com/robertpanvip/gox/runtime/signal"
)

func main() {
    signal count = 0
    let doubled = Signal.computed(func() int { return count() * 2 })

    // JSX 插值 {count}/{doubled} 由编译器编成 getter 并自动补读调用
    view := <div id="app"><span>{count}</span><b>{doubled}</b></div>

    view.BindReactive(signal.Effect)   // 一行接线

    count = 5   // 自动更新：count→"5"、doubled→"10"，无需 view.Update()
}
编译器细节：signal 语法糖在管线早期消除声明并改写读写，但 JSX 插值当时是整体 token、改写穿透不到。JSX 后端重新词法化插值时拿到同一份 signal 变量集合，补上读调用——{count} 正确编成 count() 而非把 signal 函数对象当值。scene / vdom 两个后端都已覆盖。
链路验证（runtime/scene/reactive_test.go + pkg/compiler/jsxscene_test.go）：signal 经两层组件 Props 传到叶子 → 叶子在插槽里消费 → 写入后自动刷新、组件只执行一次不重建 → 写相同值因 equalValue 裁剪零冗余写入 → Computed 派生信号同样驱动；编译器侧验证插值/属性/组件 Props 里的 signal 读补全。

三·补充二、强类型组件 Props（省略类型名 + 字段校验）

复合组件有两种契约形态，由组件函数签名自动判定，无需额外标注：

形态组件签名JSX 属性编译为语义
强类型 struct
要类型安全时		 func Card(props CardProps)
type CardProps struct{...}		 Card(CardProps{title:"x", n:42}) 属性是快照值，编译期校验字段名 / 类型 / 缺失
getter-map
要保鲜 / 响应式时		 func Card(props gxscene.Props) Card(gxscene.Props{"title": func() any{...}}) 属性是 getter，随 Update() / BindReactive 刷新

强类型形态复用了「对象字面量的省略类型名 + 期望类型补全 + 校验」机制：JSX 编译期先生成裸对象字面量 Card({title:"x", n:42})，transpiler 从 func Card(props CardProps) 签名推断期望类型 CardProps，补全为 Card(CardProps{...}) 并校验。字段拼错、类型不符、缺字段都会编译报错（带 GX 坐标）。

// gox build demo.gx -jsx=scene   ·   examples/jsxscene-typed.gx
type CardProps struct {
    title string
    n     int
}
func Card(props CardProps) *gxscene.Instance {
    return <div><h1>{props.title}</h1></div>  // 直接强类型字段访问
}
func main() {
    view := <Card title="Gox" n={42}/>   // → Card(CardProps{title:"Gox", n:42})
    // <Card title={123} n={42}/> → error: 字段 "title" 类型不匹配：期望 string，实际 int
    // <Card title="Gox"/>         → error: 缺少字段 "n"（类型 CardProps）
}
取舍：强类型属性是快照值（组件只执行一次、字段是普通值），写变量后不会自动刷新——要响应式请用 getter-map + BindReactive。两种形态可在同一文件混用，按组件各自签名判定。验证见 pkg/compiler/jsxscene_test.go 的 TestJSXSceneTypedProps*。

三·补充三、应用入口 gxapp.open（类比 ReactDOM.render）

前面都在讲「一棵场景树怎么建、怎么更新」。gxapp.open 是再上一层的应用外壳——把 JSX 挂到「窗口」上，正如 ReactDOM.render(element, container)。

源码小写、生成大写：遵循 GX「外部符号按小写书写、编译器还原真实大小写」的约定（同 gxvdom.render）——源码写 gxapp.open / gxapp.windowConfig，生成的 Go 是 gxapp.Open / gxapp.WindowConfig。运行时库里定义的仍是大写 Open（Go 导出可见性要求）。
参数含义
第一个JSX（编译后即 gxscene.Render(...) → *Instance）
第二个窗口配置 gxapp.windowConfig（标题、尺寸、位置、全屏、后端提示）
// gox build demo.gx -jsx=scene   ·   examples/jsxapp.gx
import gxapp "github.com/robertpanvip/gox/runtime/app"

app, err := gxapp.open(<div id="app">hello</div>, gxapp.windowConfig{
    Title:"Demo", Width:800, Height:600,
})
if err != nil { panic(err) }
defer app.Close()
app.Run()

窗口后端是接口，第一版内置 Headless（用 TextBackend 绘制到 io.Writer，沙箱 / CI 可跑通）。WindowConfig 字段：Title / Width / Height / X / Y / Resizable / Fullscreen / Backend；零值尺寸自动补 800×600，Backend 空值补 "headless"。

API作用
gxapp.Open(view, cfg)打开默认 Headless 窗口 + 绘制首帧，返回 (*App, error)
gxapp.OpenWith(view, cfg, win)注入自定义窗口后端（实现 Window 接口）
Window 接口Open/Draw/Run/Close/Config — Skia / wgpu / GLFW 按此接入
App.Draw() / Update()手动重绘一帧 / 更新场景树并重绘
App.BindReactive(effect)signal 变化 → 自动更新 + 重绘一帧（批处理，见下）
App.Run() / Close()事件循环 / 关闭（幂等）
gxapp.RenderText(view)不建窗口，直接绘制成字符串（测试用）
signal 自动重绘（批处理）：app.BindReactive(signal.Effect) 建一个聚合 effect——Instance.Update() 递归读所有 getter 登记依赖并裁剪写入，随后 Draw() 一帧。一次 signal 写入 = 一帧，不会出现「部分插槽已更新」的中间态画面（这是应用入口该有的语义，区别于底层 Instance.BindReactive 的逐插槽精确模式）。接线时首帧被抑制，避免与 Open 的首帧重复。真实实测：count=5 后一帧内 count=5 与 doubled=10 一致。
接入真实 GUI：实现 Window 的 Open/Draw/Run/Close/Config，用 OpenWith 注入即可——Skia / wgpu / GLFW 后端无需改动 gxapp 或编译器。当前 Headless 后端让整条链路在无 GUI 环境端到端可验证。

三·实战、把组件 + 响应式 + open 串成一个完整应用

前面几节把每个零件单独讲了。这一节给一个可直接编译运行、且实测通过的完整例子：两层复合组件（Dashboard → Stat）+ signal 响应式 + gxapp.open 应用入口。源码见 examples/jsxapp-full.gx。

完整源码

// gox build examples/jsxapp-full.gx -jsx=scene -o main.go && go run .
package main
import (
    gxscene "github.com/robertpanvip/gox/runtime/scene"
    gxapp   "github.com/robertpanvip/gox/runtime/app"
    "github.com/robertpanvip/gox/runtime/signal"
)

// ① 叶子组件：从 Props 取 getter，在 JSX 插槽里读值 value()
pub func Stat(props gxscene.Props) *gxscene.Instance {
    label := gxscene.Get[string](props, "label")
    value := gxscene.Get[int](props, "value")
    return <div class="stat"><span>{label()}</span><b>{value()}</b></div>
}

// ② 中间组件：把上层 getter 原样转发给两个 Stat
pub func Dashboard(props gxscene.Props) *gxscene.Instance {
    count   := gxscene.Get[int](props, "count")
    doubled := gxscene.Get[int](props, "doubled")
    return <section id="dash">
        <h1>Dashboard</h1>
        <Stat label="count"   value={count()}/>
        <Stat label="doubled" value={doubled()}/>
    </section>
}

func main() {
    // ③ signal 源 + computed 派生（源码小写 computed → Computed）
    signal count = 0
    let doubled = Signal.computed(func() int { return count() * 2 })

    // ④ 组合根视图：插值里读 signal，编成 getter 传给组件树
    view := <div id="app"><Dashboard count={count} doubled={doubled}/></div>

    // ⑤ 应用入口：源码小写 gxapp.open / windowConfig
    app, err := gxapp.open(view, gxapp.windowConfig{Title: "Gox Dashboard", Width: 800, Height: 600})
    if err != nil { panic(err) }
    defer app.Close()

    // ⑥ 一行接线：signal 变化 → 精确更新插槽 → 自动重绘一帧
    app.BindReactive(signal.Effect)

    // ⑦ 写入：count→5、doubled→10，两行同帧一致更新
    count = 5
}

逐段拆解

段做了什么关键点
①②定义两层复合组件 Dashboard → Stat大写标签即组件；Get[T]() 取 getter，插槽里写 value() 读当前值（写 value 会成快照不更新）
③signal count 源 + Signal.computed 派生 doubled源码小写 computed，编译器还原为 Computed
④组合根视图 <Dashboard count={count} .../>插值 {count} 编成 getter func() any{return count()}，沿 Props 传到叶子插槽
⑤gxapp.open(view, cfg) 挂到窗口源码小写 open/windowConfig，生成 gxapp.Open/WindowConfig
⑥app.BindReactive(signal.Effect) 接线聚合 effect：Update() 递归读所有 getter 登记依赖，随后 Draw() 一帧
⑦count = 5 写入自动刷新，组件只执行一次不重建，首帧被抑制避免重复绘制

实测输出（两帧）

上面示例真实编译运行，Headless 后端把场景树绘制到终端。count=5 写入前后各一帧：

# 首帧（count=0） <div id="app"> <Dashboard> <section id="dash"> <h1>"Dashboard"</h1> <Stat><div class="stat"><span>"count"</span><b>"0"</b></div></Stat> <Stat><div class="stat"><span>"doubled"</span><b>"0"</b></div></Stat> </section> </Dashboard> </div> # 写入 count=5 后（自动重绘，仅一帧） <div id="app"> ... <Stat>... "count" <b>"5"</b> ...</Stat> ... <Stat>... "doubled" <b>"10"</b> ...</Stat> </div>
验证要点：① signal 经两层组件 Props 传到叶子插槽并自动刷新；② count=5 与 doubled=10 在同一帧一致更新（聚合 effect 批处理，无中间态）；③ 组件只执行一次、不重建。源码 examples/jsxapp-full.gx 已通过 gox build -jsx=scene + go run 端到端验证。

四、响应式 UI 增强（SolidJS 化四阶段）

前面讲的是「一棵场景树怎么建、叶子怎么更新」。这一节是四阶段架构升级：把 Gox 从「带 Signal 的 JSX 框架」推进为「具有原生细粒度响应式语义的语言」。 分层边界保持一致：语言层识别 Signal，响应式层追踪依赖，UI 层更新节点。工具链 Go 1.27（支持泛型方法）。完整设计见 docs/reactive-ui-roadmap.md。

为什么要做：评审的核心判断是「Owner + Reactive Computation 才是 SolidJS 的核心」。只有把响应式作用域（Owner）、清理（Cleanup）、结构化控制流（分支 / 列表）与场景树协作起来，才谈得上细粒度——否则 signal 只是能触发整树重算的语法糖。四阶段就是按这个依赖顺序落地的。

阶段 1 · 响应式核心：Owner + Computation + Cleanup（runtime/signal）

能力API / 语义
相等性裁剪signal.New(v) 默认 reflect.DeepEqual，值未变不触发下游；signal.NewWithEquals(v, eq) 自定义策略
可销毁 EffectEffect(f) → Computation；h.Dispose() 幂等：断依赖、停订阅、执行清理
Computed 句柄Computed(f) 常规用法；ComputedWithHandle(f) → (Signal[T], Computation) 需要提前销毁时
Owner 树CreateRoot(func(o *Owner){...}) → *Owner；GetOwner() / RunWithOwner(o, f)；父销毁级联子，嵌套 CreateRoot 自动挂为子
生命周期OnCleanup(fn)（每次重跑前 + 销毁时执行）、OnMount(fn)（首次挂载执行一次）
批处理Batch(func(){ 多次 signal 写入 }) 合并同一轮写入，批次结束统一调度 Effect
import "github.com/robertpanvip/gox/runtime/signal"

// Effect 现在返回可销毁句柄；挂在 Owner 下，Owner 销毁会级联停掉它
signal.CreateRoot(func(o *signal.Owner) {
    h := signal.Effect(func() {
        fmt.Println("count =", count())
        signal.OnCleanup(func() { /* 重跑前 / 销毁时执行 */ })
    })
    _ = h
    // 之后 h.Dispose() 可单独停掉这个 effect（幂等）
})
// 一次写入只触发一次 effect：signal.Batch(func(){ count(1); count(2) })
scene.Computation 是 signal.Computation 的类型别名，因此 signal.Effect 可直接作为 BindReactive 的实参（Go 的函数类型要求返回类型完全一致）。

阶段 2 · 条件分支：if / else if / else（JSX 内）

JSX children 支持条件分支，产出 gxscene.OpBranch + gxscene.BranchGetter(selector, builders...)。切换分支时销毁旧 Owner、只重建该区域，绝不重跑根组件。

signal visible = true
signal count = 0

view := <div>
    if visible {
        <span>{count}</span>
    } else {
        <b>Hidden</b>
    }
</div>
依赖与清理：selector（visible()）在当前 Effect 上下文求值以登记依赖；索引不变时不重建——count 变化由子树自身插槽的细粒度 Effect 处理。索引变化才销毁旧 Owner（级联停 Effect / 跑 Cleanup）并在新 Owner 下构建目标子树。支持 else if 链。

阶段 3 · Keyed For：keyed 列表（含元素类型自动推断）

<For> 产出 gxscene.OpFor + gxscene.ForGetterOf[T](each, key, render)：按 key 复用节点、每元素独立 Owner。render 参数类型可省略，编译器从 each 自动推断。

type User struct { id int; name string }
signal users = []User{{1,"Tom"},{2,"Jack"}}

view := <ul>
    <For each={users} key={(u) => u.id}>
        {(u) => <li>{u.name}</li>}
    </For>
</ul>
能力说明
元素类型推断(u) 无注解时从 each 的 []User 推断出 User，生成 ForGetterOf[User]；支持 signal 变量 / 普通变量 / 函数返回值；(u User) 显式注解始终优先
keyed diffkey(item) 生成稳定键：相同键复用节点（移动而非重建），新增在独立 Owner 下构建，删除销毁 Owner（级联清理）
细粒度更新每元素独立 Owner，元素内 signal 变化只更新对应项；重排只调顺序、不重跑 render
推断优先级：render 参数显式注解 > each 集合类型（[]T / [N]T / signal 声明字面量）> 降级 any。signal 声明类型在改写前采集，避免初值字面量被 Signal.New(...) 包裹遮蔽。key lambda 参数类型同样可省略，复用 render 的元素类型。

阶段 4 · GUI 调度：结构变化重绘 + 批处理（runtime/app）

修复的关键缺陷：此前 app 只建一个聚合 effect 调 Update()，未为 Branch/For 这类结构插槽接线，导致分支 / 列表切换时场景树变了却不重绘。新增 Instance.BindStructural 仅为结构插槽接线，与叶子的聚合 effect 并存；app.BindReactive 用「重绘包装」的 effect 接线——selector / each 变化重建子树后自动画一帧。
能力说明
结构变化重绘BindStructural 接线 Branch/For 插槽；切换 / 增删后自动 Draw 一帧
关闭清理App.Close 额外 dispose 结构 effect 与元素 Owner，无泄漏
批处理Batch 合并同一轮多次 signal 写入为一帧，无「部分插槽已更新」的中间态画面
压力验证Owner 500 轮创建/销毁、分支 200 轮切换，Effect / Cleanup 严格配对

验证：go build ./... + go test ./... 全量通过（Go 1.27.4）。条件分支与 For 均有「转译 → 真实 go run → 校验输出」的端到端测试。详见 runtime/signal/owner_test.go、runtime/scene/branch_test.go / for_test.go、runtime/app/app_test.go、internal/integration/integration_test.go。

五、约束清单

  1. 组件签名二选一 func(gxscene.Props) *gxscene.Instance（getter-map，保鲜）或 func(T) *gxscene.Instance（T 为本文件具名 struct，强类型快照）；返回类型不匹配则不是合法组件。
  2. 组件只执行一次 组件体是建树逻辑；不要把「每次刷新要做的事」放这里，放到 getter 里。
  3. getter-map 形态：动态数据必须是 getter 属性传变量（title={title}）而非快照字面量；组件体用 Get[T]()() 读。Get 断言失败返回零值，不 panic。
  4. 强类型形态：字段编译期校验 属性名必须存在于 struct、值类型须兼容、所有字段须提供，否则编译报错（带 GX 坐标）；属性是快照值，不随变量变化刷新。
  5. 大写/带点 = 组件 其余 = 原生标签；与 vdom 后端判定一致。
  6. children getter-map 形态用 gxscene.Child(props)() 读（子 Instance，透明摊平）；强类型形态作为 struct 字段传入。
  7. 更新靠 Update() 或 BindReactive 驱动 scene 不内置响应式；BindReactive(signal.Effect) 可把 signal 直接接到插槽，免手动 Update。
  8. SetPart/SetGetter 用插槽下标 下标由编译期分配，手写 opcode 时才需要；JSX 开发中优先用 getter。
  9. 绘制后端目前只有 TextBackend 经 Backend 接口抽象，Skia / wgpu 可后续接入，编译器无需改动。
  10. 条件分支的 selector 必须是 signal 读 if visible { ... } 里的 visible() 在 Effect 上下文求值登记依赖；普通变量不会触发分支切换。
  11. <For> 必须有 key keyed diff 依赖稳定键复用节点；render / key 参数类型可省略（从 each 推断），显式注解始终优先。
  12. 响应式作用域挂在 Owner 上 Effect / Computed 自动挂到当前 Owner；OnCleanup 在重跑前与销毁时执行；Dispose 幂等。分支切换 / 列表删除会级联清理对应 Owner。
  13. app 层结构变化也会重绘 app.BindReactive 经 BindStructural 为 Branch/For 接线，结构变化后自动画一帧；底层 Instance.BindReactive 仍是逐插槽精确模式。
